# Approach — maximum-weight closure by a minimum cut

A set closed under the prerequisite relation is called a **closure** of the
directed graph whose arcs run from a strategy to what it requires, and this
problem is **maximum-weight closure**, better known in contest write-ups as
**project selection**. It is solved by building one flow network, taking a single
**minimum s-t cut**, and subtracting.

## The network

Nodes: the `n` strategies, plus a source `s` and a sink `t`.

| arc | capacity | for |
|---|---|---|
| `s → i` | `pnl[i]` | every `i` with `pnl[i] > 0` |
| `i → t` | `-pnl[i]` | every `i` with `pnl[i] < 0` |
| `a → b` | `infinite` | every pair `[a, b]` in `requires` |

`ceiling` is the sum of all positive `pnl`, and `infinite` is `ceiling + 1`.
Strategies with `pnl[i] == 0` get no arc of their own.

By the **max-flow/min-cut theorem** the capacity of the cheapest cut separating
`s` from `t` equals the maximum flow from `s` to `t`, so

```
answer = ceiling - maxflow(s, t)
```

and that is the entire algorithm: build, run one max flow, subtract. Hint 2 has
the argument for why the cut's source side is a valid activation set and why its
capacity is exactly the shortfall — the only part left to check is that
`ceiling + 1` is large enough, and it is, because putting every strategy on the
sink side is itself a cut of capacity `ceiling`, so no cheapest cut ever pays for
a prerequisite arc.

**The set itself, if you ever want it**, is the source side of that cut: after the
flow saturates, the strategies still reachable from `s` along arcs with residual
capacity are exactly the ones to activate. This challenge asks only for the total,
but it is worth knowing that the cut carries the decision and not just its value —
the flow number on its own means nothing here.

## Max flow

**Dinic's algorithm**. Store arcs in flat parallel arrays so arc `i` pairs with
its reverse `i ^ 1`, and give every forward arc a reverse arc of capacity `0` so
flow can be cancelled and re-routed. Then repeat two steps until the sink is
unreachable: a BFS from the source labels every node with its distance in the
residual network, and a DFS restricted to arcs that step from distance `k` to
distance `k+1` saturates every shortest route before the next BFS.

```
build the network above
flow = 0
while a BFS from s reaches t in the residual network:
    keep a per-node cursor into its arc list, all reset to 0
    walk forward from s along arcs with residual capacity that advance the level:
        at t:            push the route's smallest residual capacity along it,
                         add it to flow, and retreat to the first arc the push
                         saturated
        at a dead end:   mark the node unreachable for this phase, step back one
                         arc, and advance that node's cursor
    stop the phase when the walk backs all the way out of s
print ceiling - flow
```

**Walk; do not recurse.** The route search is the textbook shape for a recursive
DFS, and the routes here are as long as the prerequisite chains, which the README
lets run the length of the input. A recursive search is then tens of thousands of
frames deep: a `RecursionError` in Python whatever `setrecursionlimit` says, and a
blown 8 MB stack in Rust or C. The per-node cursor is what makes the flat walk
above cheap — an arc rejected in a phase is never looked at again in that phase.

## Things that go wrong

- **An `infinite` that is not big enough.** `max(abs(pnl)) + 1` is the tempting
  choice and it is wrong: a single prerequisite arc may have to carry the flow of
  many earners funnelling through it, and once its capacity is below that, cutting
  it is cheaper than the honest cut and the reported set is invalid. It survives
  every other fixture here and dies on `20_funnel_bottleneck`, where five earners
  of `100` reach five loss-makers of `-50` through one shared arc: the true answer
  is `250`, and a cap of `101` reports `399`. Both seeded recipes catch it too.
  `ceiling + 1` is always enough. Going the other way and using `2^63 - 1` invites
  an overflow the moment two such arcs meet at a node, so cap it at what the
  problem actually needs.
- **Printing the flow.** The flow is the shortfall, not the answer;
  `ceiling - flow` is. Fifteen of the eighteen fixtures separate the two, `02`
  most bluntly — no prerequisites at all, so the flow is `0` and the answer is
  `40`.
- **Pointing the prerequisite arc the wrong way.** `a → b` says "activating `a`
  drags `b` in". The reverse arc `b → a` says the opposite and reads the input
  backwards; `01`, `05`, `11_chain_transitive`, `17_dense_total_order`,
  `19_disjoint_clusters` and `20_funnel_bottleneck` all notice, and it is worth
  fixing by reasoning about which side of the cut is forced rather than by trying
  both directions.
- **Chasing the prerequisite closure yourself.** A strategy's real cost is its
  whole transitive closure, and the construction never computes one: the arcs make
  the cut respect the closure for free. Any code that walks the closure per
  strategy and adds up what it finds is both slower and wrong, because closures
  overlap and the shared part gets paid for twice — `12_star_shared_prerequisite`
  is ten earners over one shared prerequisite, and `11_chain_transitive` punishes
  checking only the direct prerequisite (`900 - 50` looks like `850`; the chain
  actually costs `750` and the answer is `150`).
- **A 32-bit accumulator.** Contributions reach `10^9` and there can be 50000 of
  them, so the ceiling reaches `5 * 10^13`. `13_i64_total` answers `2.5 * 10^9`,
  already past `2^31`, and the two recipes answer `2.68 * 10^12` and
  `1.22 * 10^12`. Capacities need the same width as the totals.
- **Special-casing the input's rough edges.** A self-reference, a repeated pair,
  a mutual pair, a longer prerequisite loop, a zero contribution — every one of
  them is handled by adding the arc the table says and nothing else. Code that
  collapses loops into components first, or that dedupes pairs, or that skips
  `pnl[i] == 0`, is code that can be wrong; code that does not exist cannot be.
  `15_self_and_duplicate_edges`, `16_zero_contributions`, `14_cycle_clusters_split`
  and `18_all_mutual` are the fixtures that watch this.

## Not the same problem as `39-hard-max-flow`

Both build a residual network and run Dinic, and that is the end of the
resemblance. `39` is a flow question: the network *is* the input, the capacities
are given, and the number asked for is the throughput — the flow is the answer, and
a min cut is at most a way of checking it. Here the network is not in the input at
all; it is constructed, its two poles are invented, and every capacity encodes
either a contribution or a constraint. What is wanted is the *cut* — which side of
it each strategy lands on is the activation set, and the flow value is only a
subtraction away from the total. `39` teaches how to push flow. This one is about
recognising that a selection problem with implications between the choices is a cut
problem at all, which is the step nothing in `39` prepares.

`62-hard-neutral-basket` is the other subset-selection challenge here, and the
contrast is the useful part. It caps `n` at 38 because the exponential search
genuinely survives: meet in the middle halves the exponent and no more, since a
target on a sum of arbitrary signed values has no structure to exploit beyond that.
Here the exponent is not halved, it is gone, and `n` runs to 50000 — because the
prerequisite constraint, which looks like the thing that makes the problem harder,
is precisely what turns out to be expressible as a capacity.
