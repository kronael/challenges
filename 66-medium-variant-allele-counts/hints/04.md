# Complexity — the same work in a different order

Both `golden/` and `rotten/` are `O(n)` time and `O(1)` extra space. They run
the same two compares on the same samples and add the same dosages; only the
grouping of the additions differs, and hint 3 shows why the grouping cannot
change the answer. There is no asymptotic gap to hide behind.

The difference is the dependency chain. `rotten/` adds every passing dosage to
one total, so each add waits for the one before it to finish: the loop runs at
the latency of `vaddsd`, one sample per several cycles however wide the core
is. `golden/` keeps eight totals, so eight adds are in flight at once and the
loop runs at the rate the loads arrive.

Measured on this box — Ryzen 9 5950X, `-O3 -march=x86-64-v3`, 200000 samples,
best of 50 calls to `solve`:

| build | `golden/` | `rotten/` |
|---|---|---|
| gcc 12.2 | 42.6 µs | 440 µs |
| clang 21 | 42.2 µs | 455 µs |
| gcc 12.2, `-mtune=skylake` | — | 451 µs |

About ten times faster, for code that does no less work. The last row is there
because the control's wall is the language's rounding rule, not a cost model:
retuning for a core with cheap gathers changes nothing.

`make vec` sees the same thing without a clock. Traced on fixture `14`,
`rotten/` retires 8.93 scalar instructions per sample and `golden/` 0.00.
