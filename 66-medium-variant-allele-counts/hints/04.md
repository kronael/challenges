# Complexity — the same work in a different order

Both `golden/` and `rotten/` are `O(n)` time and `O(1)` extra space. They run
the same two compares on the same samples and add the same dosages; only the
grouping of the additions differs, and hint 3 shows why the grouping cannot
change the answer. There is no asymptotic gap to hide behind.

The difference is the loop body. `rotten/` branches on every sample and adds
each passing dosage to one total, so each add waits for the one before it. When
every sample passes, the loop runs at the latency of `vaddsd`, about three
cycles a sample; when some fail, mispredicted branches cost more than the chain.
`golden/` has no branch and keeps eight totals, so eight adds are in flight at
once and the loop runs at the rate the loads arrive, whatever passes.

Measured on this box — Ryzen 9 5950X, `-O3 -march=x86-64-v3`, 200000 random
samples, best of 50 calls to `solve`, gcc 12.2 and clang 21 within a few
percent of each other:

| samples passing | `golden/` | `rotten/` |
|---|---|---|
| all | 42 µs | 135 µs |
| three in four | 42 µs | 345 µs |
| half | 42 µs | 570 µs |

Three to thirteen times faster, for code that does no less work.

`make vec` sees the same thing without a clock. Traced on fixture `14`,
`rotten/` retires 8.93 scalar instructions per sample and `golden/` 0.00, under
gcc 12.2 and clang 21 alike, and with `-mtune=skylake` or `-mtune=znver3` too:
the control's wall is the language's rounding rule, not a cost model.
