# Hint 4 — why the obvious alternatives are wrong here

**Cutting each link and re-testing the network** is the direct reading of the
statement, and it is what `rotten/main.py` does: count the connected groups of
venues once, then for every link rebuild the adjacency without it and count the
groups again, reporting the link when the count goes up. It is correct for every
input the README allows — parallel links and disconnected networks included — and
it is `O(m · (n + m))`, because none of the `m` traversals learns anything the
next one could reuse.

That is the wall. Measured on the two seeded recipes with an optimized native
(`cc -O2 -march=native`) transcription of `rotten/main.py`: 300 of the links
scanned takes 0.72 s on `09_large_cycle_chain` and 4.78 s on
`10_large_ring_and_hangers`, so the full scans project to about 640 s and 3900 s.
Both were still running when killed at a hard 30 s cap. The Rust and Go solver
timeout is 5 s, and the intended single walk finishes in about 0.4 s and 0.9 s in
*Python*.

**Union-find over the links in input order** finds one link per independent loop,
not every link on a loop. Add links one at a time and mark a link "redundant" when
its two venues are already joined: on the triangle `[[0,1],[1,2],[2,0]]` only
position 2 is marked, so positions 0 and 1 get reported as critical. They are not
— every link of a loop lies on that loop. Fixture `03` fails this immediately.
Union-find is the right tool for *which links a spanning forest needs*
(`19-medium-mst`), and that is a different question.

**Critical links are not critical venues.** Articulation points and bridges are
different sets and neither implies the other. In `16_loops_sharing_a_venue` two
loops meet at venue 0: removing venue 0 splits the network, so it is an
articulation point, yet no single *link* is critical and the answer is an empty
line. In fixture `06` — two venues, one link — the link is critical and neither
venue is an articulation point. The low-link machinery is shared between the two
problems, but the test at the end is not: `reach[v] > order[parent]` for a
bridge, `reach[v] >= order[parent]` (plus a separate root rule) for an
articulation point. Using the articulation-point test here reports every link
into a leaf-ward child of a cut vertex.

**Skipping the parent venue instead of the parent link.** This is the single most
common way a correct-looking implementation goes wrong, and it is why parallel
links are in the constraints. `for w in neighbours(v): if w == parent: continue`
discards *both* links when two of them join `v` to its parent, so `reach[v]` never
sees the second one, `reach[v] > order[parent]` holds, and both links are reported
as critical when neither is. Fixtures `04`, `12_doubled_middle_link`,
`15_triple_link` and `19_two_venues_doubled` catch it on inputs you can read at a
glance, and `10_large_ring_and_hangers` doubles 5000 of its links so the bug
cannot slip through to the benchmark either. Carry the *position in `links`* of
the entering link and skip exactly that slot.

**Recursion.** The natural way to write the walk is a recursive function, and it
dies here. Measured peak depth: 199998 venues on `09_large_cycle_chain` (a line of
66666 three-venue loops) and 69923 on `10_large_ring_and_hangers`. Python's
default recursion limit is 1000; raising it to 200000 trades `RecursionError` for
a segfault. A recursive C version of the walk compiled `-O2` segfaults on
`09_large_cycle_chain` under the common 8 MB stack limit — it takes several
times that stack budget to survive, which is exactly the kind of luck you do not
want your solution to depend on. Go grows goroutine stacks and gets away with it; Rust's main thread
starts with the same 8 MB budget the C version overflowed. Write the walk
iteratively.

**Reporting pairs instead of positions.** Because two links may join the same pair
of venues, `(u, v)` does not identify a link. Any intermediate representation that
loses the position — a set of `(u, v)` pairs, a `min(u,v), max(u,v)` key — cannot
be mapped back to the answer. Carry positions from the start.

**Randomized XOR labelling** is a genuine alternative, not a trap: build any
spanning forest, give every non-forest link a random 64-bit label, XOR each label
into both of its endpoints, and a forest link is a bridge exactly when the XOR of
all labels in its subtree is zero. It is also `O(n + m)`, and it still needs the
same iterative walk to build the forest and fold the subtree sums, so it buys
nothing here — and it answers with probability `1 - O(m/2^64)` instead of
certainty. Worth knowing because it extends to problems the single-pass test does
not.

**Recomputing per link, but cheaply.** Any shape of "per link, do something over
the network" is `O(m · something)` and loses. The whole point is that one walk
labels every link at once.
