# Approach — every window's word, built on its own

Build the words one base offset at a time instead of one window at a time.
Pass `i` ORs base `s + i` into window `s`'s word for every `s`; each pass is a
unit-stride sweep with the window as the loop index, and no window waits on
another:

```c
for (size_t p = 0; p < n; p++) {
	base[p] = (uint64_t)((genome[p] >> 1) & 3);
}
for (size_t i = 0; i < len; i++) {
	for (size_t s = 0; s < windows; s++) {
		code[s] |= base[s + i] << (2 * i);
	}
}
```

Then every guide sweeps the words, four windows to a 256-bit vector:

```c
for (size_t s = 0; s < windows; s++) {
	const uint64_t x = code[s] ^ want;
	uint64_t m = (x | x >> 1) & 0x5555555555555555ull;
	m = (m & 0x3333333333333333ull) + (m >> 2 & 0x3333333333333333ull);
	m = (m + (m >> 4)) & 0x0f0f0f0f0f0f0f0full;
	m += m >> 8;
	m += m >> 16;
	m += m >> 32;
	count += (m & 0xff) <= d;
}
```

x86-64-v3 has no packed popcount, and gcc 12 does not vectorize
`__builtin_popcountll`, so the count is summed inside the lane: pairs of bits
into nibbles, nibbles into bytes, bytes into the low byte. At most 20 bits are
set, so no partial sum overflows its field. The compare against `d` is one
`vpcmpgtq`, and `count` a packed sum of its masks.

`golden/solution.c` does exactly this in tiles of 2048 windows: it builds a
tile's words, then runs every guide over them while they sit in L1. Without
tiles, each guide streams the whole word array — 8 MB at a million bases —
from memory, and the time follows whatever else the machine is doing.
`make vec` grades it at 0.34 scalar instructions per base under gcc 12.2 and
0.45 under clang 21.

## The form of each step matters

Measured with the fixture `make vec` traces, `x86-64-v3`, `-O3`, every form but
the first in tiles:

| words built / mismatches counted | gcc 12.2 | clang 21 |
|---|---|---|
| sliding window, `__builtin_popcountll` (hint 5) | scalar | scalar |
| widened bases, `__builtin_popcountll` | scalar | vectorized |
| straight from the genome bytes, in-lane sum | vectorized | scalar |
| widened bases, in-lane sum (`golden/solution.c`) | vectorized | vectorized |

clang vectorizes `__builtin_popcountll` with a nibble lookup in `vpshufb`; gcc
does not. Built straight from the bytes, `code[s] |= ((genome[s + i] >> 1) & 3)
<< (2 * i)` widens four bytes per vector, and clang loads each four with
`vmovd`, a load of one 32-bit element: five scalar loads per base across 20
passes. gcc loads whole vectors there and passes at 0.70.

## Rust and Go

**Rust** (rustc 1.97): the same two phases vectorize, and LLVM vectorizes
`count_ones()` the way clang vectorizes `__builtin_popcountll`, so the plain
form works:

```rust
for i in 0..len {
    for (c, &b) in code.iter_mut().zip(&base[i..]) {
        *c |= b << (2 * i);
    }
}
code.iter()
    .map(|&c| {
        let x = c ^ want;
        u64::from(((x | x >> 1) & 0x5555_5555_5555_5555).count_ones() as usize <= d)
    })
    .sum()
```

`make vec` grades that at 0.49 scalar instructions per base. `rust/`'s
`make bench` times the debug build, where the same code takes over 5 seconds a
case. A sliding-window `solve` in Rust stays scalar, like the C one.

**Go**: the compiler does not vectorize on its own, so write the lanes with
`simd/archsimd`. With the genome copied into a `[]byte` with 16 bytes of
slack, `archsimd.LoadUint8x16(raw[p:]).ExtendLo4ToUint64()` widens four bases
to a `Uint64x4`; `ShiftAllRight(1)` and `And` with
`BroadcastUint64x4(3)` make their codes, and `Store` writes them to a
`[]uint64`. The passes are `LoadUint64x4`, `ShiftAllLeft(uint64(2 * i))`, `Or`,
`Store`. The sweep is `Xor` with `BroadcastUint64x4(want)`, the in-lane sum with
`ShiftAllRight`, `And`, `Add`, then `AsInt64x4().Greater(BroadcastInt64x4(d))`,
whose `ToBits()` the scalar `bits.OnesCount32` counts. `Uint64x4.OnesCount` is
`VPOPCNTQ`, AVX-512, and `make vec` stops at it. Pad the arrays to a multiple of
four windows and take back what the padding windows counted. One such version
passes `make vec` at 0.62 scalar instructions per base.
