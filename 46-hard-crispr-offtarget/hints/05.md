# Hint 5

**A window of up to 20 bases fits in one 64-bit word.** Give each base two
bits — bits 1 and 2 of the ASCII code already tell them apart, so
`(c >> 1) & 3` maps A, C, G, T to 0, 1, 3, 2 — and put base `i` of the window in
bits `2i` and `2i + 1`. XOR a window's word with the guide's: bit pair `i` is
nonzero exactly where the two differ. `(x | x >> 1) & 0x5555555555555555`
leaves one bit per mismatching base, and a popcount counts them. One window
against one guide is a handful of word operations, whatever `L` is, so the full
scan is `O(guides × genome)`.

The obvious way to get every window's word is to slide: shift the previous
window's word right by one base and put the new base on top. It is correct
and fast — in C for `x86-64-v3`, about 2.4 seconds on each large case — and it
fails `make vec`, because each window's word is the previous window's word
shifted: a chain through the whole genome, not a reduction the compiler may
split. Neither compiler vectorizes the loop:

```
cc -O3 -march=x86-64-v3 -I../../shared/c -fopt-info-vec-missed -S -o /dev/null solution.c
solution.c: missed: not vectorized: unsupported use in stmt.

clang -O3 -march=x86-64-v3 -I../../shared/c -Rpass-analysis=loop-vectorize -S -o /dev/null solution.c
solution.c: remark: loop not vectorized: value that could not be identified as reduction is used outside the loop
```

**No window's word needs the window before it.** Window `s` is bases `s`
through `s + L − 1`, and nothing else. How could every window's word be built at
once, with the window as the loop's own index?
