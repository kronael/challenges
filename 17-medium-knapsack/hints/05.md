# Approach — read one row, write another

With one row, every cell the loop writes lives in the array it reads. Walking
the budgets downward makes that correct one budget at a time, but four at once
leave the compiler something to prove about a distance it sees only at run
time. Give it nothing to prove: keep two rows. Each item reads `best`, the
answers for the items before it, and writes `next`; budgets below the item's
weight copy across unchanged; then the two swap. Every budget of an item now
depends only on the row before it, which is how the same recurrence is spread
across the cores of a GPU (Boyer, El Baz and Elkihel, 2012).

```c
if (weight > capacity) continue;
memcpy(next, best, w * sizeof *next);
for (size_t c = w; c <= cap; c++) {
	const long long take = best[c - w] + v;
	next[c] = take > best[c] ? take : best[c];
}
/* swap best and next */
```

The update is a select, not a conditional store: every budget writes `next[c]`
whether or not the item helps. gcc 12.2 turns the loop into `vpaddq`,
`vpcmpgtq`, and `vpblendvb` over four 64-bit lanes, clang 21 into the same with
`vblendvpd`, each behind a check that `best` and `next` do not overlap, which
two separate allocations pass. `make vec` grades both at 0.01 scalar and 0.61
packed instructions per item-capacity pair. `golden/solution.c` is this loop.

## The shape of the update matters

Measured with the fixture `make vec` traces, `x86-64-v3`, `-O3`:

| inner update | gcc 12.2 | clang 21 |
|---|---|---|
| one row, `if (take > best[c]) best[c] = take;` | scalar | scalar |
| one row, `best[c] = take > best[c] ? take : best[c];` | vectorized | scalar |
| two rows, `next[c] = take > best[c] ? take : best[c];` | vectorized | vectorized |

The first row is hint 2's loop: gcc does not vectorize the conditional
store at all. In the middle row gcc's run-time check is on the sign of the
weight: reading `best[c - w]` below every budget it writes, the downward loop
never reads a cell this item has already changed, so any positive weight passes
and the vector loop runs. clang
checks instead that the range it reads, `best[0..cap-w]`, and the range it
writes, `best[w..cap]`, do not overlap. In one row they overlap for every item
no heavier than half the capacity, so clang runs its scalar copy of the loop
while its remark still says the loop was vectorized.

The lanes are 64 bits because the sums need them: the fixture's answer is
28806383737, past `2^31`. AVX2 has no 64-bit max, so the max is a compare and a
blend; `_mm256_max_epi64` in C and `Int64x4.Max` in Go are AVX-512, which
`make vec` refuses.

## Rust and Go

**Rust** (rustc 1.97): zip the three slices, and LLVM vectorizes the loop the
way clang does. `make vec` grades it at 0.02 scalar per item-capacity pair.

```rust
next[..w].copy_from_slice(&best[..w]);
for ((slot, &keep), &base) in next[w..].iter_mut().zip(&best[w..]).zip(&best[..=cap - w]) {
    *slot = keep.max(base + item.value);
}
std::mem::swap(&mut best, &mut next);
```

The one-row loop, `best[c] = best[c].max(best[c - w] + item.value)` over
`(w..=cap).rev()`, stays scalar.

**Go**: the compiler does not vectorize anything on its own, so write the lanes
with `simd/archsimd`. Once per item, `v := archsimd.BroadcastInt64x4(it.Value)`;
then for each four budgets from `w` up, load `keep := archsimd.LoadInt64x4(best[c:])`
and `take := archsimd.LoadInt64x4(best[c-w:]).Add(v)`, and store
`keep.IfElse(keep.Greater(take), take)` into `next[c:]`. The last
`(capacity + 1 - w) % 4` budgets take a scalar loop. `make vec` grades it at
0.02 scalar.

## Things that go wrong

- **One row, upward.** A budget then reads a cell that has already taken the
  item, so an item can be packed twice. Case `01` catches it.
- **The budgets below the weight.** Without the copy, `next[c]` for `c < w`
  still holds the row from two items back.
- **32-bit lanes.** Eight fit a register where four 64-bit lanes do, and the
  fixture's sums overflow them.
- **The tail.** `capacity + 1 - w` is rarely a multiple of four. The fixture's
  weights run from `1` to one past its capacity and leave every remainder.
