# Complexity

**O(n) time.** Every index is pushed exactly once and popped at most once, so the
inner `while` runs at most `n` times across the entire scan — at most `2n` stack
operations for the whole book, with one multiply and one comparison per pop. One
pass, nothing re-read.

**O(n) space.** A book whose quantities never fall keeps every level on the stack
at once; recipe `09` is precisely that shape, a million indices deep. There is no
smaller bound worth chasing, since the input itself is `O(n)`. The two-array
variant is the same asymptotically — three passes and `2n` extra integers — and a
little slower in practice for the extra memory traffic.

## Why the obvious alternatives lose

**Walking outward from every level** is the literal reading of hint 1's
reduction, and it is what `rotten/main.py` does: for each level, step down while
the neighbours rest at least as much, step up while they do, then size that
block. Correct for every input the README allows, and `O(n²)`, because each level
rediscovers a run its neighbour just finished walking. The shape that kills it is
not exotic: a book that keeps deepening as it goes is an ordinary resting book,
and there every upward walk runs to the far end.

**Enumerating runs directly** — for each start `l`, extend `r` while tracking the
running minimum — is the same `n²/2` with a tighter inner loop and no reduction
at all. It is not a repair, it is the thing hint 1 ruled out.

**Divide and conquer on the shallowest level.** Take the shallowest level in the
book, score `its quantity * the whole width`, then recurse on the part below it
and the part above it. This is correct, and it is not even slow: the recursion
touches `O(n)` intervals, so with an `O(1)` range-minimum structure over `O(n log
n)` preprocessing it lands at `O(n log n)`. Two things sink it here. Its
recursion depth is the longest chain of splits, which on a monotone book is `n` —
a million frames, which is a `RecursionError` in Python and a blown stack in Rust
or C, and recipe `09` is monotone by construction, so this is not a hypothetical.
And a sparse table answers any range minimum for any query, when the only queries
in this problem are the ones the recursion invents for itself.

**Union-find, deepest level first.** Sort the levels by quantity descending and
add them back one at a time, unioning each with whichever neighbour is already
present and scoring `quantity * component size`. Every active level rests at
least as much as the one being added, so the component is exactly the run that
level limits — the same candidate set as the stack, arrived at differently. This
one is a real alternative rather than a mistake: `O(n log n)` for the sort plus
near-linear union-find, comfortably inside the budget. It is worth knowing
because it survives generalisations the stack does not, and worth skipping here
because it needs a sort, a parent array, and a size array to do what one pass and
one stack already do.

**Reusing `59-medium-price-undercut` and multiplying.** If you still have that
challenge's answer array — the wait until each day is undercut — then
`quantities[i] * wait[i]` looks like this problem solved for free. It is exactly
the `top - 1` bug from `03.md`: it measures level `i`'s run from `i` upward and
ignores every level below `i` that the run also covers. The `59` scan is half of
the machinery here, not a shortcut past it.

## The wall

`rotten/main.py` re-walks every run from scratch: `O(n²)` against the intended
`O(n)`, which at `n = 1000000` is about `n²/2 = 5 * 10¹¹` comparisons against
`2n = 2 * 10⁶` stack operations.

| recipe | shape | n | answer | golden | naive, native |
|---|---|---|---|---|---|
| `09_large_rising_wall` | every level rests strictly more than the one before, all million quantities distinct | 1000000 | 125216313354562 | ~0.47 s | 81 s |
| `10_large_draining_plateaus` | 1000 non-increasing plateaus of 1000 equal quantities, a hundred pairs of them joined into 2000-level runs | 1000000 | 557235409000 | ~0.40 s | 49 s |

Measured with a temporary optimized native control on the two seeded inputs, run
to completion rather than projected. The literal transcription of
`rotten/main.py` (`cc -O2 -march=native`, 64-bit quantities) sustains 1.96 * 10⁹
comparisons per second and takes 253 s and 256 s on the two recipes. Narrowing
the quantities to 32 bits and compiling `-O3 -march=native -funroll-loops` — the
fastest thing anyone would plausibly hand-write while still walking outward from
each level — reaches 6.2 * 10⁹ and 1.0 * 10¹⁰ comparisons per second, and those
are the 81 s and 49 s in the table. Every one of those runs was still going when
killed at a hard 5 s cap. Against the 5 s Rust/Go/C solver budget that is a
margin of roughly 10x for the fastest native brute force and 51x for the literal
one, while `golden/main.py` finishes in *Python* in under half a second — so
essentially none of the gap is parsing.

`rotten/main.py` itself sustains about 6 * 10⁶ comparisons per second, which puts
the full scan somewhere near 23 hours. `make bench` does not wait: the runner
kills the process group at the timeout.

The two recipes fail differently on purpose. `09_large_rising_wall` never falls,
so nothing is ever popped until the closing drain: the stack grows to a million
entries, every candidate in the book is computed in that final flush, and there
is not one equal pair of quantities anywhere — this is the recipe that tests
space and the sentinel. `10_large_draining_plateaus` never rises, so the stack
stays shallow and pops on nearly every level — and 999100 of those million pops
land on an exactly equal quantity, with a hundred of the plateaus running 2000
levels wide because two of them join. This is the recipe that tests the
strict/non-strict pairing. A solver that gets one right and the other wrong has
the boundary rule half-built.
