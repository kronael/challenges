# Approach — a monotonic stack, where one pop hands you both boundaries

Keep a **stack of level indices whose quantities strictly increase from the
bottom up**. Scan the book once. An index goes on when it is reached and comes
off when the level that blocks it on the right shows up — and the instant it
comes off, *both* of its boundaries are known.

That last sentence is the whole technique. The level popped is `top`:

- the index that pops it **is** `top`'s right blocker, because the scan reached it
  first and it rests no more than `top`;
- the index left sitting under `top` on the stack **is** `top`'s left blocker,
  because everything between the two was pushed after `top`, so it rested at
  least as much as `top`, so it has already been popped.

Two boundary searches, no searching. This is where the problem stops being
`59-medium-price-undercut` with an extra multiply: there, the stack answered one
question per element and the popped index only needed the *popper*. Here the
popped index also needs its *neighbour on the stack*, and the pair is what turns
a boundary into a width.

```
best  = 0
stack = []                              # indices; quantities increase upward
for right in 0 .. n:                    # n inclusive: a virtual closing level
    height = quantities[right] if right < n else 0
    while stack is not empty and quantities[stack.top] >= height:
        top  = stack.pop()
        left = stack.top if stack is not empty else -1
        best = max(best, quantities[top] * (right - left - 1))
    stack.push(right)
print best
```

**Read the pop test against hint 2.** Popping on `>=` means equal levels knock
each other off, so the stack holds strictly increasing quantities — which is
exactly why the neighbour under `top` is `top`'s strictly-smaller left blocker,
while the popper only has to be smaller-or-equal on the right. That is the
"strict on one side, non-strict on the other" combination. Popping on `>` gives
the mirror pairing and is equally correct. Popping is what has to happen *before*
the push, though: push first and the level immediately pops itself, and every
fixture fails.

**The virtual closing level is not optional.** Running the loop to `n` with a
height of 0 is what empties the stack, and every candidate that reaches the last
level of the book is computed during that drain — on a book whose quantities only
rise, *every* candidate is. Stopping at `n - 1` loses fixtures `02`, `04`, `05`,
`12`, `13`, `14` and `16`. Draining in a separate loop afterwards is equally fine
as long as it uses `n` as the right boundary. If you pop on `>` rather than `>=`,
note that a closing height of 0 no longer clears the stack outright, because a
level may rest nothing and 0 is not strictly below 0 — it happens not to change
the answer, since those levels are worth 0 anyway, but a closing height of `-1`
or an explicit drain says what you mean instead of relying on that.

**The two-array variant is just as good and easier to debug.** Fill `left[]` in a
forward pass and `right[]` in a backward pass, each with the same stack, then take
the best `quantities[i] * (right[i] - left[i] - 1)` in a third loop. Three passes
and `2n` extra integers, but each pass is the plain nearest-smaller scan you
already know from `59`, so the two arrays can be checked independently before the
product is anywhere near them. The one thing to get right is the strict/non-strict
pairing from hint 2 — non-strict in *both* directions is the combination that
collapses plateaus.

## Things that go wrong

- **Taking the left boundary from `top - 1` instead of from the stack.** The
  seductive version of this bug reads "the run starts where `top` is", giving
  width `right - top`. It is right whenever the winning run happens to start at
  its own shallowest level and wrong the moment the run extends below it, which
  is most books: fixtures `02`, `03`, `06`, `07`, `12`, `13_i64_area`, `14`,
  `16`, `17`, `18` and `19` all catch it. The left boundary is *never* derived
  from `top`; it is read off the stack after the pop.
- **A 32-bit product.** A quantity fits in 32 bits and a width fits in 32 bits,
  and their product does not: `10^9` resting at each of `10^6` levels is `10^15`.
  Fixture `13_i64_area` is `5 * 10^9`, already past `2^31`, and it is the only
  small fixture that catches this — the large cases answer `1.25 * 10^14` and
  `5.57 * 10^11`, so a truncating solver fails them with a plausible-looking
  wrong number. In C, cast before multiplying, not after.
- **Skipping levels that rest nothing.** A level resting 0 contributes a
  candidate worth 0, so it is tempting to `continue` past it — but it is also a
  blocker for everything around it, and dropping it out of the scan lets a run
  span it. In fixtures `03` and `12` an empty level is the only thing keeping two
  runs apart, and both come out too large if it is filtered away; fixture `17`
  puts empty levels at each end instead, where they meet the sentinels.
- **Treating `q` as a free choice.** Any search over quantities as well as runs —
  a binary search on `q`, a pass per distinct quantity — is doing work hint 1
  eliminated. The quantity is a consequence of the run, never a parameter.
- **Recursing.** See the divide-and-conquer note in `04.md`: at `n = 1000000` a
  recursion whose depth tracks the book is a stack overflow, and the seeded books
  are the exact shapes that make it so.
