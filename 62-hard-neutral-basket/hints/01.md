# Hint 1

> Spoilers. Open only when stuck, and only one file at a time.

**Read the two limits against each other.** `n <= 38` and
`|exposures[i]| <= 10^12` are a strange pair, and they are the whole design of
this challenge.

`n <= 38` is tiny. No sorting, no scanning, no clever ordering of 38 numbers is
going to be the hard part — the input is a few hundred bytes. A bound that small
is the problem-setter telling you the answer is *exponential in n*, because if a
polynomial answer existed the bound would be 200000 like every other challenge
here. So you are being invited to enumerate something.

But you cannot enumerate baskets. There are `2^38` of them, which is 275 billion,
and that is not a number you get through inside a five-second budget no matter
how tight the inner loop.

And you cannot enumerate *nets* either. The reflex from bounded-total problems —
walk the positions keeping a table of every total reachable so far, one cell per
total, which is exactly what `17-medium-knapsack` does — needs one cell per
reachable net. Nets here run from `-3.8 * 10^13` to `3.8 * 10^13`. That table
does not fit, and swapping it for a hash set of reachable nets does not help:
there are up to `2^38` distinct nets to store.

So both standard moves are blocked: too many baskets to list, too many nets to
index. Something else has to be small.

Write `2^38` and `2^19` next to each other. The second is 524288 — a number you
can not only enumerate but *sort*. What, in this problem, is there exactly
`2^19` of?
