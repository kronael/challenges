## 07:29 2026-07-25

Every challenge that ships a Rust stub now also ships a C stub, and the two
Python-only API exercises now ship a Go stub. 54 new solver directories.

The io C track hangs off one interface, identical in all 48 challenges:

    void   input_parse(const JsonValue *root, Input *in);
    void   input_free(Input *in);
    Answer solve(const Input *in);
    void   answer_print(FILE *out, const Answer *a);
    void   answer_free(Answer *a);

Because `Answer` carries its own printer, `main.c` and `test.c` are fully
generic and byte-identical everywhere, as are `Makefile`, `json.h` and
`harness.h`. Only `solution.h` and `solution.c` are per challenge, so a new io
challenge means writing two files, not seven. `json.h` is a hand-rolled DOM
parser — unescapes in place over the source buffer since decoding never grows
the text, keeps both the exact `long long` and the `double` for each number, and
parses a 10⁶-element fixture in about 50 ms, so `make bench` measures the
solver rather than the parser.

Decisions worth remembering:

- `input_parse` transcribes JSON literally. No adjacency lists, no sorting, no
  prefix sums — a derived field in the scaffold would hand the solver the
  approach. Recorded in CLAUDE.md so it survives the next scaffolding pass.
- `lint` is a second compile with `-Wpedantic -Wshadow -Wstrict-prototypes
  -Werror -fsyntax-only`, since neither clang-tidy nor cppcheck is installed and
  `fmt` already degrades gracefully when clang-format is missing.
- The C dirs use `CC ?= cc`, not the `CC ?= gcc` the sys goldens use. gcc is not
  installed on this box. (Correction, 2026-07-26: this does NOT block `make sys`
  — `?=` is a no-op against Make's built-in `CC` default of `cc`, so the sys
  goldens build with clang and both `make sys` and `make sys-rotten` pass here.
  An earlier version of this entry wrongly said they couldn't run.)
- 33's C stub deliberately has no thread-registration call. An earlier draft had
  one, which quietly pointed at per-thread slots; the Rust stub gets by without
  it, so the C one does too. It does expose instrumented `node_alloc`/`node_free`
  so the stress test can prove the leak/double-free invariant.
- 22's Go stub uses `iter.Seq` (go.mod 1.23). The exercise is about laziness and
  a pull-based closure would have made the point worse.
- 21's Go test drops the Python suite's `test_relational_not_imperative` check —
  it greps for the `python-constraint` import, which has no Go equivalent.

Verified rather than assumed: all 48 io `make test` runs reach every small
fixture and fail only on the stubbed body, with zero parse errors and zero
warnings; all 6 sys stress and bench binaries build clean and abort on the
unimplemented operation; both Go stubs build, vet and panic as intended.
