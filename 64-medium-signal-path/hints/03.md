# Approach — one bottom-up pass, two numbers per desk

Settle the desks so that every desk is reached after both of its sub-desks, then
apply hint 2's two lines. That is the whole algorithm: a single sweep of the
hierarchy, `O(1)` work per desk, no desk visited twice.

The ordering is easier than it looks. A **preorder** — the order a plain
stack-driven walk from the root produces — lists a desk before all of its
descendants. Read that list backwards and every desk comes after all of its
descendants, which is precisely what the recurrence needs. Nothing about left
versus right matters, and nothing about the numbering matters.

```
order = []                                  # a preorder of every desk
stack = [root]
while stack is not empty:
    v = stack.pop()
    order.append(v)
    push left[v] onto stack if it exists
    push right[v] onto stack if it exists

down = [0] * n
best = None
for v in order reversed:                     # every sub-desk already settled
    a = down[left[v]]  if left[v]  exists and down[left[v]]  > 0 else 0
    b = down[right[v]] if right[v] exists and down[right[v]] > 0 else 0
    candidate = pnl[v] + a + b
    if best is None or candidate > best: best = candidate
    down[v] = pnl[v] + max(a, b)
print best
```

`down` starts at zero everywhere and that is safe, because a desk's slot is only
ever read after it has been written — a leaf writes `pnl[v]` into it before any
parent asks.

**Iterate; do not recurse.** The recurrence is the textbook shape for a recursive
post-order, and at these limits recursion is the one thing that will kill an
otherwise correct solver. The hierarchy is allowed to be a single 500000-desk
line, and recipe `09_large_skewed_chain` is exactly that, so a recursive walk is
500000 frames deep: a `RecursionError` in Python whatever you set the limit to
(CPython's own C stack goes first), and a segfault in Rust or C on an 8 MB thread
stack. `61-hard-critical-venue-links` documents the same trap for its depth-first
search and handles it the same way, with an explicit stack. If you want the
recursive version anyway, it is a legitimate way to *write* the recurrence and a
poor way to *run* it — get it working small, then flatten it.

**Other correct orderings.** The two-pass shape above is the shortest to get right,
but a genuine single-pass post-order works too: keep a stack of `(desk, stage)`
pairs, or push each desk twice and act on the second sighting. Both settle the same
order with the same `O(1)` work per desk; the two-pass version just separates
"decide the order" from "run the recurrence", which makes each half checkable on
its own. There is one ordering that looks free and is not: deriving a parent array
and sweeping desks by number. See hint 2 — the numbering carries no ordering
guarantee, and `15_shuffled_numbering` and `19_wide_shuffled` are there to say so.

## Things that go wrong

- **Clamping one line and not the other.** The `> 0` test belongs in both
  `candidate` and `down[v]`, because both consume the same child gains. Clamping
  only the candidate under-reports what travels upward; clamping only `down`
  over-reports the candidate. `04`, `07`, `14_negative_arm_left_out` and
  `17_zero_contributions` fail on the missing clamp in either place.
- **Letting `down[v]` take both arms.** Covered in hint 2, and worth restating
  because it is the one mistake that still passes a hand-drawn example: a desk
  with only one profitable arm behaves identically either way, so the bug hides
  until two arms are profitable at once and a third desk above them is in play.
- **Clamping the desk itself.** `down[v] = max(0, pnl[v] + max(a, b))` is
  *correct* here, but only by accident: it changes nothing because every reader of
  `down[v]` clamps again. `candidate = max(0, pnl[v] + a + b)` is not correct, and
  is the empty-chain bug from hint 2 wearing a different hat.
- **A 32-bit accumulator.** Contributions reach `10^9` and a chain can hold
  500000 of them, so totals reach `5 * 10^14`. `13_i64_total` is `5 * 10^9`,
  already past `2^31`, and it is the only small fixture that catches this — the two
  seeded recipes answer `6.08 * 10^11` and `2.76 * 10^11`, so a truncating solver
  fails them with a plausible-looking wrong number. In C, make `pnl` and the
  accumulators `long long`; the desk numbers are fine as `int`.
- **Reading `root` as desk `0`.** It is in the input for a reason:
  `15_shuffled_numbering` and `19_wide_shuffled` put it elsewhere.
- **Walking each sub-desk's branch to answer `down`.** This is the naive reading
  of hint 1 and it is what `rotten/main.py` does — see `04.md` for why it loses and
  what shape of firm punishes it.

## Not the same shape as the other tree challenges here

`50-hard-tree-sequence-likelihood` is also a bottom-up pass over a tree, and the
resemblance stops at "bottom-up". There, each node carries a vector over four
discrete states, a child is folded in by *summing* over its states, and the folded
children are then *multiplied* together — a sum-product recurrence in which every
child always contributes to the single value that travels upward, so there is no
choice to make and no candidate answer separate from it. Here each desk carries one
integer, children are folded in with `max` and a clamp at zero, and the value that
travels upward is deliberately *not* the candidate answer: the split between "what
I can claim as a finished chain" and "what I can offer my parent" is the entire
difficulty, and it exists because a chain may not re-enter a desk. Sum-product has
no such restriction.

`60-medium-venue-ancestor` shares only the input family. It is a query problem over
a tree — climb two routes until they meet — with no recurrence and no per-node
value at all, and it encodes its hierarchy as a parent array because its chains
run upward. This challenge encodes the hierarchy as `left` and `right` because its
recurrence runs downward and needs a desk's two sub-desks kept apart.
