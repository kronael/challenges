# Complexity — the same work in a different shape

Both implementations classify every byte, check it against its offset's
class, and return the same answer: `O(bytes)` time for both, plus `O(width)`
extra space for `expect`. There is no asymptotic gap to hide behind.

`golden/` wins because the inner loop's trip count is `width` and every operand
is a unit-stride read at the loop's own index, so thirty-two consecutive bytes
can be classified side by side. The control's cursor makes byte `i + 1`'s offset
depend on byte `i`'s, and its `switch` is control flow gcc will not fold into a
select; either one alone keeps the loop scalar under gcc, and the cursor alone
keeps it scalar under clang.

Measured on this box — Ryzen 9 5950X, `-O3 -march=x86-64-v3`, a 1 MiB stream
with six separators per frame, the median of five runs, each the best of 30
calls to `solve`:

| width | gcc `golden/` | gcc `rotten/` | clang `golden/` | clang `rotten/` |
|---|---|---|---|---|
| 13 | 902 µs | 856 µs | 278 µs | 1378 µs |
| 24 | 333 µs | 822 µs | 231 µs | 1417 µs |
| 32 | 123 µs | 758 µs | 175 µs | 1394 µs |
| 64 | 104 µs | 799 µs | 149 µs | 1404 µs |
| 128 | 97 µs | 785 µs | 144 µs | 1425 µs |
| 512 | 83 µs | 793 µs | 128 µs | 1379 µs |

Below 32 bytes the frame-major loop never fills a 32-byte vector: at width 24
gcc falls back to 16-byte vectors, and at width 13 its version runs no faster
than the cursor. That is why the constraints start at 32 bytes, where every
frame holds at least one full 32-byte block.

`make vec` sees the same thing without a clock. Traced on fixture `15`,
`rotten/` retires 9 scalar instructions per byte under gcc and 24 under clang,
and `golden/` 0.10 and 0.32.

A fixed-width layout exists so that frame boundaries and field offsets are
known before a byte is read; a loop that still discovers them by walking a
cursor pays for state it already had.
