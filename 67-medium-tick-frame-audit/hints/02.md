# Hint 2

**Ask what `pos` is.** A cursor that ticks up and wraps back to `0` at `width`
is a value the compiler can only produce by running the previous iteration: it
is neither an induction variable, which is a fixed step from the index, nor a
reduction, which it could split and recombine. So byte `i + 1`'s offset is not
known until byte `i`'s has been computed, and thirty-two offsets can never be
worked out side by side.

Confirm it: `cc -O3 -march=x86-64-v3 -fopt-info-vec-missed -S solution.c`
reports `unsupported use in stmt` for a cursor loop, and clang's
`-Rpass-missed=loop-vectorize` refuses it too.

**The offset is arithmetic on the index, not state.** Frame `f` starts at byte
`f × width`, and its byte `j` sits at offset `j`. Neither needs the byte before
it. What loop structure makes the offset the loop's own index?
