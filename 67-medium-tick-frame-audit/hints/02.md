# Hint 2

**Ask what the offset is.** A cursor that ticks up and wraps back to `0` at
`width` is a value the compiler can only produce by running the previous
iteration: it is neither an induction variable, which is a fixed step from the
index, nor a reduction, which it could split and recombine. So byte `i + 1`'s
offset is not known until byte `i`'s has been computed, and thirty-two offsets
can never be worked out side by side.

Confirm it from `c/`: `cc -O3 -march=x86-64-v3 -I../../shared/c
-fopt-info-vec-missed -c solution.c -o /dev/null` reports `not suitable for
gather load` for a read indexed by such a cursor, and clang's
`-Rpass-missed=loop-vectorize` refuses the loop too. gcc names only the first
obstacle it meets: a `switch` in the loop shows up as `control flow in loop`,
and a per-frame flag that the frame edge resets as `unsupported use in stmt`.

**The offset is arithmetic on the index, not state.** Frame `f` starts at byte
`f × width`, and its byte `j` sits at offset `j`. Neither needs the byte before
it. What loop structure makes the offset the loop's own index?
