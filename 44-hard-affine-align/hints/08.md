# Approach — striped columns, then settle the strip tops

`golden/solution.c` walks `t` one column at a time over a striped `s`, sixteen
16-bit lanes per AVX2 vector. `h` holds `max(M, X, Y)` of the column just
finished and `y` its `Y`, both in the striped order of hint 7. `p` is the
profile row of the column's residue.

```c
__m256i down = _mm256_insert_epi16(neg, top, 0);
for (size_t k = 0; k < seg; k++) {
	const size_t at = k * LANES;
	const __m256i h_left = load(h + at);
	const __m256i mv = _mm256_adds_epi16(diag, load(p + at));
	const __m256i yv = _mm256_max_epi16(_mm256_subs_epi16(h_left, open),
					    _mm256_subs_epi16(load(y + at), extend));
	store(h + at, _mm256_max_epi16(mv, _mm256_max_epi16(down, yv)));
	store(y + at, yv);
	down = _mm256_max_epi16(_mm256_subs_epi16(_mm256_max_epi16(mv, yv), open),
				_mm256_subs_epi16(down, extend));
	diag = h_left;
}
```

`Y` opens from the whole cell to the left, `h_left`: opening from `Y` itself
never beats extending it, so no separate `M` or `X` is kept. `X` opens from the
`M` or `Y` of the row above.

`diag` enters as the last vector of `h` shifted up one lane, with the gap row
above the grid in lane 0: the row above the top of strip `L` is the bottom of
strip `L - 1`. `down` carries `X` from vector to vector. Strip 0 starts from
`top`, the gap row above the grid less a gap opening; every other strip starts
at minus infinity, so the top rows of strips 1 to 15 still miss the `X` that
comes from the strips above them.

Farrar's paper settles those with a *lazy* loop: shift the last `X` candidate
up one lane, walk the column again while it still beats something, and repeat
up to 16 times. Here `X` opens from `M` and `Y` (hint 3), and both read only
the column before, so `X` never feeds back into anything inside a column, and
each strip's entry value can be computed exactly. `down[L]` is what strip `L`
alone hands the next one. The entry of strip `L` is
`max over L' < L of down[L'] - e·seg·(L - 1 - L')`, and adding `e·seg·(L + 1)`
first turns it into a plain prefix maximum across lanes: one shift, then four
shift-and-max steps.

```c
__m256i scan = LANE_SHIFT(_mm256_adds_epi16(down, climb), neg, 1);
scan = _mm256_max_epi16(scan, LANE_SHIFT(scan, neg, 1));
scan = _mm256_max_epi16(scan, LANE_SHIFT(scan, neg, 2));
scan = _mm256_max_epi16(scan, LANE_SHIFT(scan, neg, 4));
scan = _mm256_max_epi16(scan, LANE_SHIFT(scan, neg, 8));
__m256i carry = _mm256_subs_epi16(scan, drop);
for (size_t k = 0; k < seg; k++) {
	store(h + k * LANES, _mm256_max_epi16(load(h + k * LANES), carry));
	carry = _mm256_subs_epi16(carry, extend);
}
```

`climb` holds `e·seg·(L + 1)` per lane and `drop` holds `e·seg·L`.
`LANE_SHIFT(v, fill, n)` moves lane `k` to lane `k + n`: `vperm2i128` puts the
low half of `v` over the low half of `fill`, and `vpalignr` shifts each
128-bit half by `2n` bytes. The answer is the lane and vector that row
`|s| - 1` maps to, after the last column.

## Rust, Go, and C

**Rust**: `std::arch::x86_64` has every intrinsic above —
`_mm256_adds_epi16`, `_mm256_subs_epi16`, `_mm256_max_epi16`,
`_mm256_permute2x128_si256::<0x02>`, `_mm256_alignr_epi8::<14>`. Call them from
an `unsafe` block. Every target builds with `-C target-cpu=x86-64-v3`, where
they inline; `#[target_feature]` is neither needed nor accepted. Measured with
rustc 1.97: 0.28 scalar instructions per residue pair.

**Go**: `archsimd.Int16x16` has `AddSaturated`, `SubSaturated`, and `Max`, with
`archsimd.LoadInt16x16(h[at:])` and `Store`. The lane shift is
`v.ConcatPermute128Scalars(2, 0, fill)` for the half move, then
`v.AsUint8x32().ConcatShiftBytesRightGrouped(t.AsUint8x32(), 16-2*n).AsInt16x16()`
with `n` a constant; for `n = 8` the half move alone. Measured with Go 1.27.1:
about 0.8 scalar instructions per residue pair, of which the `idx` map lookups
are 0.12; `strings.IndexByte(aa, c)` costs less.

**C**: every target builds `c/` for `x86-64-v3`, so the code above compiles
there as it is, with `<immintrin.h>`.

In all three, a plain row-by-row DP stays far over one scalar instruction per
residue pair.
