# Hint 3 — why the obvious alternatives are wrong here

**Rebuilding one route per pair and searching it** is the direct reading of the
statement, and it is what `rotten/main.py` does: collect the whole route of `a`
into a fresh list, then step up from `b` and search that list at each step. Both
halves are wasteful, and the second is quadratic — every step before the answer
scans the entire route and finds nothing, so a pair whose shared venue sits near
the root costs `depth × depth`. On the deep-line recipe that is about 1.1·10¹²
element comparisons, which is over a minute even as optimized native code.

**A set of `a`'s ancestors per pair** fixes the quadratic and is genuinely
correct: build a hash set of the route of `a`, then climb from `b` until a venue
is in the set. It is O(depth) per pair like the intended solution, so it is not
the trap — but it allocates and fills a container for every pair, and it always
walks `a` all the way to the root even when the answer is one step below `a`. The
two-pointer climb needs no allocation and stops as soon as the pointers agree.

**Painting `a`'s route into a shared `seen` array** looks like the fix for the
allocation, and then the clearing gives the saving straight back: wiping an
`n`-entry array between pairs is O(n) per pair whatever the depths are, the
same cost profile as rebuilding a fresh set each time. Clearing only the
venues you painted is fine — but that is the same bookkeeping as the set,
with a subtler bug waiting if a pair ever reuses stale marks.

**Recursion for the depth pass.** A recursive walk over children, or a recursive
`depth(v) = depth(parent[v]) + 1`, is the natural way to write phase 1, and it
costs you in Python: the hierarchy may be a single 200000-venue line, and
`RecursionError` fires around a depth of 1000, long before either large recipe
finishes. C, Rust, and Go carry more call-stack headroom by default (Go's grows
on demand), so the same recursion can survive there at these depths — but it is
still needless per-call overhead for a walk you can do in one iterative pass.
Write the pass iteratively regardless of language.

**Binary lifting, sparse tables, and Euler tour + RMQ are out of scope.** They
answer each pair in O(log n) or O(1) after O(n log n) preprocessing, and they exist
for the case this challenge deliberately does not create: a very deep hierarchy
*and* a query batch large enough that O(depth) per pair is too slow. Here `q` is
at most 5000, so the plain climb is what the limits ask for. Reach for the jump
tables when the batch has hundreds of thousands of pairs against a deep tree —
and note the extra machinery they need: a `log n`-wide ancestor table, or an
Euler tour plus a range-minimum structure, both easy to get subtly wrong for no
gain at these limits.

**It is not `18-medium-task-ordering`.** That one needs an adjacency list,
in-degrees, and an ordering over a general DAG. Here every venue has exactly one
outgoing link, there is nothing to order, and a cycle is ruled out by the input
contract, so none of that machinery applies. Building a children list and running
a traversal is a lot of code for a `depth` array you can fill by following the
links you were already given.
